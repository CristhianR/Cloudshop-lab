🌐 Visitar tienda

ClienteRoute 53CloudFrontAWS WAFACMInternet GatewayALB públicoEC2 Web · AZ1EC2 Web · AZ2ALB internoEC2 App · AZ1EC2 App · AZ2RDS primariaElastiCache
  1. El navegador resuelve el dominio en Route 53 (consulta DNS).
  2. CloudFront recibe HTTPS y AWS WAF evalúa la solicitud; ACM aporta el certificado.
  3. Para una petición dinámica no cacheada, CloudFront llama al ALB público a través del IGW.
  4. El ALB público envía la petición a una EC2 Web de cualquiera de las dos AZ.
  5. Nginx llama al ALB interno, que distribuye a una EC2 App.
  6. Node.js consulta Redis o PostgreSQL y responde por la ruta de retorno.

💡 WAF y ACM se resaltan por asociación, no como saltos de red.

📦 Consultar catálogo

  1. Angular solicita GET /api/products a través de CloudFront.
  2. WAF inspecciona; CloudFront reenvía la petición al ALB público.
  3. ALB público → Nginx → ALB interno → Node.js.
  4. Node.js consulta Redis; si no hay entrada, lee RDS primaria y actualiza caché.

🛒 Realizar compra

ClienteCloudFrontAWS WAFInternet GatewayALB públicoEC2 Web · AZ1ALB internoEC2 App · AZ1EC2 App · AZ2RDS primariaRDS standbyBanco externoNAT Gateway AZ1NAT Gateway AZ2
  1. El usuario confirma carrito y envía POST /orders con una clave de idempotencia.
  2. CloudFront/WAF → ALB público → EC2 Web → ALB interno → Node.js.
  3. Node.js crea una orden pendiente en RDS primaria.
  4. El banco procesa la tarjeta mediante checkout alojado/tokenización; la llamada saliente del backend usa NAT e IGW.
  5. El backend verifica el resultado o webhook firmado y confirma el estado en RDS.
  6. RDS replica síncronamente a la standby en la otra AZ.

💡 No guardar PAN/CVV. Usar idempotencia, verificación de firmas y conciliación bancaria.

  2. WAF inspecciona la solicitud HTTPS a CloudFront.
  3. CloudFront devuelve la imagen desde caché o consulta S3 mediante OAC.

👤 Registro nativo

ClienteCognitoGoogleCloudFrontEC2 App · AZ1
  1. El cliente abre el formulario de registro.
  2. Cognito User Pool recibe los datos por HTTPS y aplica políticas de contraseña/MFA.
  3. Cognito verifica la cuenta según su configuración y emite tokens.
  4. La API Node.js valida la firma, audiencia y claims del JWT.

💡 Cognito es regional pero no vive en subredes de la VPC. Google no participa en el registro nativo.

🔐 Iniciar con Google

ClienteCognitoGoogleCloudFrontEC2 App · AZ1
  1. El cliente inicia el flujo OAuth 2.0 / OIDC con Cognito.
  2. Cognito redirige al navegador hacia Google para autenticación y consentimiento.
  3. Google devuelve una respuesta a Cognito.
  4. Cognito emite tokens a la aplicación; Node.js verifica los JWT.

💡 No se envían contraseñas de Google a CloudShop.

💳 Pagar con tarjeta

  1. El cliente solicita iniciar el pago de una orden pendiente.

🛡️ Falla de AZ1

ALB públicoALB internoEC2 Web · AZ2EC2 App · AZ2NAT Gateway AZ2RDS primariaRDS standbyInternet Gateway
  1. AZ1 falla y los health checks dejan de considerar sus targets saludables.
  2. Los ALB dirigen nuevas peticiones a EC2 disponibles en AZ2.
  3. RDS inicia failover para promover la standby en AZ2.
  4. La aplicación restablece conexiones, aplica reintentos seguros e idempotencia.
  5. Auto Scaling recupera capacidad cuando sea posible.

💡 Multi-AZ protege frente a fallos de AZ; no equivale a DR multirregional.

Cómo interpretar el diagrama

AWS Cloud es el contenedor mayor. Dentro mostramos una región, que contiene la VPC y dos AZ. Cada AZ tiene subredes públicas, web, aplicación y base de datos. La VPC se extiende entre las AZ: no está dentro de una sola zona.

Los ALB se muestran como recursos lógicos centrados, no como una tercera zona física: el ALB público utiliza subredes públicas de ambas AZ y el interno subredes privadas de ambas AZ. WAF y ACM aparecen fuera del recorrido de paquetes porque son asociaciones de seguridad/certificados.

CloudFront y Route 53 son globales y se representan en el espacio AWS fuera de la VPC; Cognito es regional, fuera de la VPC. Las cajas no representan literalmente la ubicación de infraestructura administrada global.
